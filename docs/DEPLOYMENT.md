# Combined application deployment

Use one public application origin for marketing/app pages, Better Auth, the versioned API and Socket.IO. `npm run build` compiles frontend/server; `npm start` serves them together. PostgreSQL stores host accounts, workspaces, boards, Brand Kits/assets and audit history; live rooms remain in the Node process. Use one app instance until an explicit shared room-state design exists.

Production requires NODE_ENV=production, DATABASE_URL, a stable random AUTH_SECRET, an exact public HTTPS APP_ORIGIN and configured SMTP_HOST/EMAIL_FROM (paired SMTP_USER/SMTP_PASSWORD where required). EMAIL_TRANSPORT must be smtp in production; file/memory are rejected. SMTP uses implicit TLS or required STARTTLS. Set PUBLIC_APP_URL to the same HTTPS origin for QR links. Optional public build metadata uses the same origin. All authentication/API browser requests are relative; no third-party cookies are required. Terminate TLS at a trusted reverse proxy preserving the public Host and secure request origin. Forwarded IPs are not trusted by default; only an explicitly configured loopback proxy policy is currently supported.

Run `npm run db:migrate` from a development/release checkout, or `npm run db:migrate:production` from the compiled runtime, as an explicit release step using reviewed committed migrations and database backups. Startup never auto-syncs tables. `/health` and `/api/health` preserve process liveness; `/ready` separately checks database/schema access and can report unavailable without treating the Node process as dead. Secure cookies are only issued in production mode with an HTTPS origin; local compiled verification uses test mode over HTTP and separately tests production cookie construction/restoration.

The old static Netlify plus unrelated onrender.com auth API topology is unsupported. Cookie auth must not depend on third-party behavior. If static hosting is retained in a later deployment, deliberately configure a same-origin API/WebSocket reverse proxy or a reviewed same-site custom-domain model. Static SPA fallback alone cannot host accounts/cloud boards. `netlify.toml` remains a legacy static routing file, not a complete deployment recipe. REALTIME_ONLY split mode is rejected in production.

Keep production database credentials server-only and enforce appropriate PostgreSQL TLS/private networking. No database or auth libraries belong in `VITE_` values. No live services, external accounts, production secrets or deployment automation were provisioned in this pass. [AUTHENTICATION.md](AUTHENTICATION.md) records pre-public-launch gaps; the historical [split guide](NETLIFY-PRODUCTION.md) is retained for context only.

The existing Docker runtime now includes migrations and their compiled runner, without development tools or local database files. The Render blueprint is adjusted to build/serve the combined application and requires manually supplied origin/database/auth/email values; it does not provision a database or automatically run migrations. Docker/Render execution was not performed locally because Docker is unavailable and live deployment is out of scope.

## Phase 3 Event snapshots

Apply reviewed `0003_events_experience_builder.sql` explicitly before running the updated application. Readiness now requires the Events schema. Launch snapshots and their copied images add persistent database storage; plan monitoring, backups and retention before volume use. Live Event state still resides on one Node process. Guest image availability follows its in-memory room and is lost on restart; this is not durable Event recovery. Keep the same-origin public application/socket topology and validated HTTPS APP_ORIGIN. No deployment/migration hook is installed by this phase.

## Phase 6 release gate

Use the [production runbook](PRODUCTION-RUNBOOK.md) for explicit migration/hash compatibility, safe Node startup, `/healthz` versus `/readyz`, SIGUSR2 drain, bounded shutdown, durable queue inspection/retry and backup expectations. Docker/Render start Node's safe entrypoint directly. Preserve one authoritative node and wait for active rooms before maintenance; no rolling live-room handoff exists. Readiness rejects incompatible schema/unsafe DB durability while liveness keeps existing rooms available through dependency failure. Hosted SMTP/proxy/TLS/devices, protected database and observed backup restoration remain P0 external-pilot gates; this phase does not deploy or declare unconditional production readiness.
