# Operational observability

Product workspace activity answers who changed something. Operational logs answer what failed and whether it can recover. Worker retries do not append workspace activity. Session completion/deletion each append one transactional product event; retries never duplicate it.

## Structured logs and safe fields

Production lifecycle, API failures, denied access, readiness edges, history enqueue/materialization, DB interruption and shutdown use timestamped JSON. The logger copies only fixed fields: level, timestamp, event, requestId, workspaceId, actorUserId, sessionId, attempt, durationMs, count, code and result. It never serializes arbitrary caller objects or Error messages. Logging/presentation failures cannot reject gameplay or committed history. API failure logs are capped per category; counters still include suppressed events. Development-only startup prints local phone URLs; production does not.

Request IDs are generated by the server and included in safe API error envelopes and `X-Request-ID`, including maintenance responses. History deletion carries its request ID into its minimal audit metadata. Realtime run UUIDs are independent of display codes. No untrusted incoming correlation ID is accepted as authority.

Never log cookies, passwords, SMTP/DB URLs, invitations/email links, bearer/capability tokens, player names/answers/drawings, SQL or parameters. UUIDs are operational identifiers, still subject to access-controlled log retention. PostgreSQL/proxy/provider logs need their **own** redaction policies; application sanitization cannot configure those systems. In particular, database error-statement logging can include SQL parameters; review provider settings before confidential use.

| Category                                           | Meaning/action                                                                      |
| -------------------------------------------------- | ----------------------------------------------------------------------------------- |
| CONFIG_INVALID                                     | Invalid startup configuration; fix values without printing secrets                  |
| DB_UNAVAILABLE                                     | Connection/refusal or otherwise unavailable DB operation; check service/network     |
| DB_TIMEOUT                                         | Statement, lock, idle/total transaction deadline; inspect contention/latency        |
| DB_CONFLICT                                        | Uniqueness/serialization/deadlock; inspect the affected bounded operation           |
| HISTORY_PAYLOAD_INVALID / HISTORY_PAYLOAD_MISMATCH | Quarantined summary; do not modify immutable results to make it fit                 |
| HISTORY_MATERIALIZE_FAILED                         | General materialization category; concrete failure code logged when known           |
| MIGRATION_REQUIRED / MIGRATION_FAILED              | Hash/version incompatibility or explicit migration failure; keep service not-ready  |
| SHUTDOWN_TIMEOUT                                   | Forced exit after deadline; check durable jobs on next startup                      |
| RATE_LIMITED                                       | Existing request category; respect retry guidance and check actual abuse/NAT impact |

`history.handoff_failed` identifies enqueue failure; `history.materialization_failed` includes attempt/result retry or failed. Unknown errors are deliberately coarse; operator reproduction and database service telemetry may be needed. Logs contain no stack/SQL dump. No comprehensive APM claim is made.

## Aggregate metrics

Every minute, a fixed JSON `operations.snapshot` contains active room/Event/socket counts; pool total/idle/waiting; queue counts/oldest age per status; cumulative materialization count/failure/duration, enqueue failures, API failures, room creation failures and cleanup time. These values reset with the process, while queue counts come from PostgreSQL. Durations are sums/individual log samples, not fabricated production percentiles. A failed snapshot logs dependency failure without taking the process down.

No public metrics endpoint or internal admin console exists. Ship stdout to a restricted provider log sink. The operator CLI prints queue aggregates and at most fifty failed identities/categories (no payload):

```sh
npm run ops:history -- inspect
npm run ops:history -- retry <session-uuid>
npm run ops:history -- prune
# Compiled runtime equivalents:
npm run ops:history:production -- inspect
```

Retry requires an explicit UUID and intact failed payload; it resets its bounded eight-attempt cycle. It cannot bypass deleted/retired receipts or hash validation. Prune is bounded; pending and processing work are excluded. Ordinary workspace users cannot invoke these commands via HTTP.

Alert on nonzero terminal failures, rising oldest pending age, repeated enqueue failure, prolonged not-ready, sustained pool waiting, process deadline exits and recurrent auth/rate-limit failure. Baseline thresholds need pilot evidence; no external alerts or provider integration were provisioned. Start with investigation within the thirty-day failed-payload window, much sooner for a missed recap.

## Health and evidence

`/healthz` says the process can answer. `/readyz` says it is not draining and dependencies/schema/default content pass a bounded probe. Neither exposes versions/counts/topology. Do not use a dependency outage as a reason to continually restart healthy in-memory rooms. Provider restart health uses liveness; traffic/deployment decisions must additionally check readiness and active-room drain evidence.
