# Content platform

An Original is a game engine. A Content Pack supplies that engine’s prompts. A pack revision is an immutable, validated JSON document. A launch copies playable prompts and exact pack/revision metadata into the in-memory room or persistent Event launch snapshot. Gameplay performs no pack queries. Studio boards remain a separate authored question format.

`shared/content-packs.ts` defines the six strict discriminated content schemas, metadata, readiness checks, portable exports, filters and permanent default identities. The fields follow existing engine behavior: Hotwire/Odd One In have choices and a correct index; Room Temperature has choices without an answer; Sellout and Scribble Shift have text prompts; Caption This references one of fifteen existing scenes. No executable content, remote image URL or custom audio reference is accepted.

`server/content-packs/service.ts` enforces current workspace permissions and active ownership. System packs are readable by authenticated accounts; workspace packs require membership. Owners/Admins manage all content; Hosts create/edit/use; Viewers read. System content is never editable through workspace APIs. Copying requires source read and destination create and starts a new identity/revision 1. Returned records omit private source IDs. Workspace row locks serialize mutation authorization with role/archive changes. Event copies copy private pack dependencies into the target once per source, preserving built-in references.

Pack saves compare `baseRevisionId`, append a revision only when the canonical parsed document hash changes, and atomically update metadata/current pointer. Archived packs retain history and reject new launches. Previously launched content is independent of later edits or archival. The same serialized draft coordinator serves Event and pack editing; caches include account/workspace/document identities. Drafts allow incomplete items; ready documents require complete, distinct choices and a valid answer index. Errors pause autosave and retain edits for Retry, export or explicit latest-version replacement.

`content_packs` stores ownership, discovery metadata, status, current pointer and provenance. `content_pack_revisions` stores schema version, validated JSONB, SHA-256 hash, item count and author. PostgreSQL enforces ownership consistency, game/status values, same-pack deferred current pointer, positive unique revision numbers and ordinary revision immutability. The additive `0004_adorable_eternity.sql` migration creates these tables; earlier board/Brand/Event/history rows are not rewritten.

Catalog queries return at most fifty summaries with deterministic update-time/UUID keyset pagination. Name/description/tags use bounded, escaped case-insensitive SQL search alongside exact game/category/season/difficulty/source filters. The workspace catalog includes readable built-in and workspace packs. Detailed documents are fetched only on demand by authenticated readers; the static preview renders at most five sample items with host answer keys. Players receive only existing engine-redacted gameplay state.

New Event items may specify `contentPackId`. Legacy items lacking it resolve the permanent default for their game, retaining `settings.pack` topic filtering and fallback. Snapshots record pack ID, revision ID/number, schema version, display name and copied prompts. No historical definition or snapshot migration is required. Standalone `room:create` optionally accepts `{contentReference:{workspaceId,selections:{[gameId]:packId}}}`. Missing selections resolve defaults in the current/personal workspace. Selection is validated before room-code allocation.

Operational audit records cover created/updated/archived/copied packs, with IDs and limited metadata, never full questions or answers. Existing no-store JSON, session/Origin protection, safe errors and API limits apply. Pack mutations additionally allow ninety requests/minute per actor/IP. Limits of 500 items, 100 active workspace packs, 320 KB HTTP bodies and fifty catalog results are technical safeguards, not paid entitlements. Room state and rate limits remain per-process.

## API

All routes are under `/api/v1`, authenticated and private. `/content-packs` supports GET system summaries, GET `/:packId`, and POST `/:packId/copy` with `targetWorkspaceId`. `/workspaces/:workspaceId/content-packs` supports GET combined summaries, POST `{document}`, GET `/:packId`, PUT `/:packId` with `{document,baseRevisionId}`, POST `/:packId/archive`, POST `/:packId/copy` and POST `/import` with a strict portable export. Nonmembers and unavailable private IDs are non-enumerating.

Readiness requires the content schema and six ready seeded defaults. Application startup never seeds. Run migrations and the explicit reviewed seed before starting a new release. No deployment hooks were added.
