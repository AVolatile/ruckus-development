# Events & Experience Builder

An Event is a saved workspace plan, not a live room. Open `/app/w/:workspaceId/events`, create an event or choose a Ruckus starter, and add up to 50 ordered Originals/Studio segments. Stable item IDs permit duplicates. Move up/down controls work by keyboard; each segment can be disabled, duplicated, removed or customized. Disabled sources remain in the definition but do not participate in launch validation. Missing sources are reported and never silently removed.

Originals expose existing round count, pace and content packs. Studio items reference board identity until launch. Optional display titles, transition labels and private host notes accompany the lineup. Event title/subtitle, planning description, Brand selection, introduction/intermission/final messages and settings are persisted. Hosts always control boundaries; Ruckus attribution stays visible. Personal and shared workspaces use the same builder.

Owners/Admins can read/create/edit/archive/launch. Hosts can read/create/edit/launch; Viewers can read/preview. Source read plus destination create permits copying. APIs enforce current membership independently of route guards. Archive is soft and prevents new launches; there is no purge/restore UI. A technical safeguard permits 500 active events per workspace, unrelated to pricing.

Each save checks its base revision and appends immutable JSONB only when content changes. Autosave serializes after 750 ms, retains edits made during a request and announces acknowledgement. Internal links flush or stay on failure. Conflicts keep the local draft for JSON export or explicit latest-cloud replacement. Optional account/workspace/event tab recovery survives refresh/re-authentication; an advanced cloud base requires conflict recovery. It is not guaranteed storage before cloud acknowledgement. Browser unload warns on unconfirmed edits. Configuration controls are disabled during explicit save/copy/launch operations.

Preview creates no socket, snapshot or room. It checks enabled sources, outlines intro/lineup/intermission/finale, shows current authorized Brand styling, and links to existing two-screen Studio previews. Validity is checked again transactionally at launch. No Brand selection uses ordinary Ruckus styling; the workspace default is offered as a choice rather than silently applied.

Six Ruckus starters are authored product examples: Team Warmup, Friday Wind Down, New Hire Mixer, Holiday Party, Company Trivia Night and Offsite Social. They contain real Originals and create fresh editable Event identities. Add Studio questions for your own occasion; no employer/customer events are invented.

Copy within a workspace makes a fresh Event/revision 1 with shared readable source references. Copy to another workspace explicitly copies every referenced Studio board into a fresh destination identity/history, deduplicating repeated source IDs. It requires board read/create as well as Event read/create and clears Brand selection. Missing sources block cross-workspace copy with a repair message, including disabled missing sources. Source history remains unchanged.

## Launch and privacy

`POST /api/v1/workspaces/:workspaceId/events/:eventId/launch` requires the current `baseRevisionId`. A workspace-locked transaction authorizes launch, resolves enabled sources and stores an immutable launch snapshot. It pins Event revision/definition, validated full Studio documents and board revisions, resolved Original settings and actual prompts (including private answer keys), and the selected Brand revision/configuration. Private host notes and answer keys never enter guest event metadata. Existing engine redaction still governs current-game answers/reveals.

Referenced processed logo/background bytes are copied to immutable `event_snapshot_assets`; all other workspace imagery remains private. Random UUID asset URLs are bearer capabilities, suitable for presentation imagery the host intends the whole event to see. Anyone receiving a URL can view that one image while its in-memory Event room remains available; do not use confidential artwork. URLs do not permit browsing workspace assets. Responses revalidate availability, use WebP/nosniff/CSP/hash ETags and return no source metadata. Ending/expiring the room invalidates delivery; a server restart makes it unavailable. There is no public bucket or persistent guest asset service.

The HTTP adapter allocates a room only after the snapshot transaction commits, returns a host capability, and the browser resumes it before opening the stage. Capacity is checked before snapshotting and allocation. A failure between commit and allocation can leave an immutable, unusable launch record; no assets become guest-readable without a live room. There is no distributed transaction between PostgreSQL and process memory. Each explicit launch creates a new snapshot/room; HTTP launches are not retry-idempotent. Lifecycle commands within a room do reject stale retries.

Launch records prepare future session history. They are not saved answers, analytics or restart recovery. See [runtime](EVENT-RUNTIME.md), [database](DATABASE.md) and [Phase 3 report](PHASE-3-REPORT.md).
